EVIDENCE AND CHOICE
On 28 October at 19:05:52 UTC, the private-admin gateway returned the sanitized
category policy-unavailable-TimeoutError during an ordinary authenticated GET.
Its Access application/policy GET exceeded the existing five-second deadline.
The upstream reason is unknown; this does not establish the cause of every prior
failure. The diagnostic deployment was removed and is not part of this repair.

The smallest chosen change is one retry of the idempotent policy GET after a
transient failure. A second fresh request can recover an isolated timeout without
retaining authorization after revocation. The five-second per-attempt limit is
unchanged. Increasing a single timeout would merely wait longer on the same
stalled request. A positive policy cache would introduce an avoidable revocation
window, shared state and invalidation rules; none is added. No SDK/dependency,
binding or architectural change is needed. This is not a guarantee of availability.

EXACT BEHAVIOR
- Healthy lookup: one GET, same full policy validation as before.
- Retry once only for TimeoutError, transport TypeError, or HTTP 502/503/504
  without Retry-After. Pause 250–500 milliseconds with jitter before the retry.
- No retry for 401/403/404, redirects, 429, HTTP 500, a Retry-After response,
  invalid JSON, success:false, mismatched/changed policy, or invalid identity.
  A repeated transient failure denies access. There is no automatic UI retry.
- Each attempt includes response-body reading within the five-second deadline.
  Late completed evidence is rejected even if an underlying reader ignores abort.
- Overall policy authorization budget per Worker: 10.5 seconds, shortened to the
  JWT expiry when earlier. No new attempt starts after that deadline. The token's
  expiry is checked again after waiting. Scheduler/network delays can make a denial
  arrive later, but cannot extend the evidence or token validity used to allow it.
- Only the policy GET is retried, never a draft save, moderation write or other
  operation. Failed policy verification does not forward into Weekly or access
  private storage. Error responses stay generic/private/no-store, without tokens,
  exception details, personal data or diagnostic fields. No new logging.
- JWT signature, issuer, audience, required claims, owner identity, pinned app,
  Google identity provider, exact owner policy, TOTP requirement/session length,
  policy-change timestamp checks and CSRF remain enforced.

VALIDITY, REVOCATION AND OUTAGES
Application authorization-cache lifetime: zero; no response or successful grant
is reused between requests, including concurrent requests. Fetch requests use
cache:no-store. Evidence is accepted only for the current verification, completed
inside the five-second attempt window and 10.5-second overall budget, before JWT
expiry. A failed first attempt supplies no usable evidence for the second.

There is no added cross-request cache revocation delay. A changed/revoked response
is denied immediately without another try; later requests must read policy again.
A change concurrent with a GET can still race the response, and Cloudflare API
propagation is outside this code's control. Do not promise instantaneous global
revocation. Each accepted read window is at most five seconds; an already admitted
operation cannot be retroactively cancelled. Existing session-predates-policy
checks are preserved. During a sustained outage both reads fail and access remains
denied, even when a previous request succeeded. There is no stale-if-error mode.

REQUEST BUDGET AND LIMITS
Maximum policy API calls per authentication check: two (normally one).
A private-editor request crosses one such check. A moderation request crosses
both the private gateway and Weekly, each independently verified: normally two
policy GETs, at most four. If both layers need a retry, their policy portions can
consume up to 21 seconds altogether, plus unchanged JWT-key retrieval and normal
application work. A page loading multiple protected assets/APIs has multiple checks.
Existing JWKS verification is unchanged and is not retried by this repair.

Cloudflare currently documents 1,200 API requests per five minutes per user/account
token and 200 per second per IP; the user limit is shared with other API/dashboard
activity. Four policy calls per moderation request would consume that entire
1,200 budget after 300 such requests without other activity; this is NOT a reserved
capacity or promised allowance. 429/Retry-After is denied without retry, preventing
this repair from repeatedly retrying a known quota block. There is no new global
throttle or cache, and repeated owner requests during an outage still consume
their bounded per-request attempts. Stop refreshing during a sustained outage.
