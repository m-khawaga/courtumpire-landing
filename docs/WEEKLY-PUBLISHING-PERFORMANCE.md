## Measured causes and focused repair

The earlier live 210.644 ms CPU sample was correlated with the private publication
preview, not traced to a particular operation. It is not a component profile.

A local V8 sampling profile and separately timed components identified:

1. Paragraph emphasis repeatedly scanned all entity names at each text character.
2. Every displayed result/source date constructed another Intl formatter. Desktop
   and mobile presentations both incur this work.
3. Preview rendered a public article in `prepare`, discarded it, then rendered the
   preview article again. It also calculated a publication hash and stored snapshot
   that the preview response never used.

The repair builds one request-local prefix index for emphasis, escapes unchanged
text in spans, reuses two date formatters for Europe/Berlin, and renders preview once.
Only formatters are reused across requests; no article, identity or policy evidence
is cached. Other timezones retain their original formatting behavior.

Publication and update still perform the entire server-side validation, source and
ranking checks, hashing, snapshot construction, cover validation and atomic SQL batch.
Authentication, current-policy lookup, MFA, CSRF, immutable metadata, stale-edit checks,
idempotency and ambiguous-outcome handling are unchanged. No client HTML is trusted.
Preview checks its own rendered size; publication independently checks the final
public rendering and full storage size, as it must even after a successful preview.

## Method and limitations

`scripts/weekly-publishing-profile.mjs` accepts a private draft JSON path. It calls the
actual publishing API with the actual migrations and SQL transactions in in-memory
SQLite, including real publish and update operations and revision-count assertions.
It also runs RS256 verification, exact-owner checks, all independent-MFA policy checks
and HS256 CSRF verification against local test keys and a fixture policy response.
There are no Cloudflare requests, production credentials, remote writes or real news
generated by this harness.

The reviewed private fixture contains 102 singles matches, a separate doubles match,
both ten-player ranking tables, sources, prose, schedules and a coverage ledger. Its
historical evidence limitations remain unchanged; successful validation is not fact
verification. Larger PRIVATE SYNTHETIC fixtures contain 306/510 singles matches plus
the same separate doubles record. All three pass validation and the existing size
limits. Their minified input/HTML sizes are respectively 59,188/180,994 bytes,
117,237/425,963 bytes, and 175,270/671,156 bytes.

Primary figures below are local high-resolution elapsed time, not Cloudflare CPU.
Windows process CPU samples were also captured but have approximately 15 ms granularity;
zero samples do not mean zero CPU. The Node process includes runtime/GC overhead.
Local SQLite is not remote D1; real JWKS/policy network latency, the private Worker
service bridge and Cloudflare isolate scheduling are not represented. Total timings
include authorization, request JSON round-trip, API work, response serialization and
response decoding. They are not a measurement of the entire deployed HTTP stack.

Each repeated median is five operations after the first sample. Separate fresh
processes start with preview, publish or update; cold update seeds an existing SQL
revision without executing the renderer first. Module import, fixture validation,
key creation and test-cover generation happen before measurement. Therefore “cold”
means first API operation in that process, not a measured Cloudflare cold isolate.
The diagnostic sampling profiler was disabled for the reported before/after figures.
These small local samples are directional, not a latency SLO or reliability proof.

## Assessment and alternatives

This removes the dominant local repeated work, but **Free-plan headroom is not
established and remains doubtful for the complete supported range**, particularly
cold requests, larger articles and large covers. Cloudflare documents a 10 ms Free
HTTP CPU allowance; HTTP 200 alone does not prove sustainable operation within it.
See [Workers limits](https://developers.cloudflare.com/workers/platform/limits/).

Do not respond with repeated speculative deployments or remove validation/auth checks.
If a bounded CPU measurement is wanted, use the procedure below. Otherwise the
recommended next design decision is a resumable server-owned preparation pipeline:
separate authenticated requests validate immutable source chunks, prepare server
rendered sections, and persist private intermediate artifacts. The final transaction
checks source hash, validator/renderer version, ranking baseline, expected publication
version and completed stages before atomically exposing the edition/registry. Any edit,
expiry or changed baseline invalidates preparation. Full-article/global checks still
need a measured bounded stage; simply splitting functions does not establish CPU fit.
This preserves admin-only publishing but adds job/recovery/retention complexity and
requires its own local implementation and approval. It is not implemented here.

Other options: keep the existing reviewed static/export workflow (least runtime risk,
but does not meet deployment-free publishing); or a separately approved trusted build
executor that performs server validation/rendering asynchronously and returns signed,
hash-bound output (more services, credentials, quota review and operational work).
Neither option may trust browser-generated HTML. A paid CPU allowance would simplify
the synchronous design but is outside the approved free-only scope and is not selected.

## Reproduce locally

From the feature worktree, with Node 24 and installed dev dependencies:

```powershell
node scripts/weekly-publishing-profile.mjs PRIVATE_DRAFT.json .weekly-private/performance/report
```

Create the output directory first. Optional final argument `3`/`5` expands only the
private synthetic match fixture and reconciles its ledger. `PROFILE_SAMPLES=1`
writes an ignored CPU profile; omit it for comparable elapsed timings.
`PROFILE_COLD_FIRST=publish` starts with publication; `update` plus `PROFILE_SEED`
pointing to an earlier `.private-seed.json` starts with a seeded revision.
`PROFILE_SOURCE` selects an extracted baseline source tree; it defaults to this
worktree. `PROFILE_LARGE_COVER=1` exercises the near-maximum PNG size.
Reports, private SQL seeds and profiles must stay under ignored `.weekly-private`.
The harness is local test code and is not imported by either Worker.
